## **Application class**

Позвольте познакомить вас с тем, кто уже очень давно помогает вам запускать и поддерживать в рабочем состояние ваши приложения. Прошу любить и жаловать, класс `Application`!

Класс **Application** — это основной класс в _Android_-приложении, который хранит все компоненты, все ваши активити, сервисы, провайдеры и прочие броадкасты.


В основном этот класс используется для инициализации глобального состояния до того, как будет показано первое активити. Во многих случаях вам не понадобится реализовывать свою имплементацию класса `Application`, но такая возможность есть.

Причины, по которым вам может понадобится свой класс `Application`:

- Выполнить какую-то логику до того, как у вас будет запущено первое активити.
- Глобальные переменные, которые пригодятся вам из разных экранов вашего приложения. К примеру, у вас есть база данных, и вам она нужна из нескольких активити. Создавать экземпляр класса для доступа к базе данных — не самое лучшее решение, поэтому вы можете создать его единожды в классе `Application` и использовать его там где это нужно.
- Хранение констант, хотя для этого лучше использовать `Object`.

Пока вы не узнаете, что такое _DI_ (_Dependency Injection_) и с чем его едят, хранить какие-то глобальные объекты в классе Application можно для целей обучения, но в работе старайтесь этого избегать, этот класс не подходит для надежного и долговременного хранения. Итак, как же нам его создать?

> [!warning] Синглтон `App.instance` ниже — антипаттерн
> Раздел нужен, чтобы понять, как это делали раньше и что ты увидишь в легаси-коде. **Писать так в новом проекте не надо.**
>
> Что не так с `companion object { lateinit var instance }`:
> - **Невозможно подменить в тестах.** Чтобы протестировать код, читающий `App.instance.something`, нужен настоящий `Application` — или придётся городить костыли.
> - **Скрытая связность.** Читая `App.instance`, ты не видишь в сигнатуре функции, что у неё есть зависимость.
> - **Ложное обещание времени жизни.** `Application` живёт столько же, сколько процесс. Если система убьёт процесс — на `App.instance` будет NPE (об этом конспект пишет в самом конце).
> - **Нет владельца ресурсов.** У синглтона нет жизненного цикла, значит нет места, где вы гарантированно закроете соединение с БД.
>
> Современная замена — DI-контейнер (Hilt). Доступ остаётся таким же удобным, но зависимости **явны** в конструкторе и **подменяемы** в тестах:
>
> ```kotlin
> @Singleton
> class UserRepository @Inject constructor(
>     private val api: UserApi,   // зависимость видна прямо здесь
> ) { /* ... */ }
> ```
>
> ```kotlin
> @HiltViewModel
> class ProfileViewModel @Inject constructor(
>     private val repo: UserRepository,  // получен из графа, а не из глобального поля
> ) : ViewModel()
> ```

Для начала создадим сам класс. Как правило, называют его очень прозаично, а именно `App`, и наследоваться он должен от класса `Application`. Также нужно будет переопределить несколько методов:

`class App : Application() {`
   `// Этот метод вызывается при старте приложения до того, как будут созданы другие компоненты приложения`
   `// Этот метод необязательно переопределять, но это самое хорошее место для инициализации глобальных объектов`
   `override fun onCreate() {`
       `super.onCreate()`
       `// Required initialization logic here!`
   `}`

   `// Вызывается при изменении конфигурации, например, поворот`
   `// Этот метод тоже не обязателен к предопределению`
   `override fun onConfigurationChanged ( newConfig : Configuration) {`
       `super.onConfigurationChanged(newConfig)`
   `}`

   `// Этот метод вызывается, когда у системы остается мало оперативной памяти`
   `// и система хочет, чтобы запущенные приложения поумерили аппетиты`
   `// Переопределять необязательно`
   `override fun onLowMemory() {`
       `super.onLowMemory()`
   `}`
`}`

По большому счёту всё готово, но работать это ещё не будет. Нам нужно сообщить всем в манифесте, что теперь это наш класс `Application` и он будет всем рулить. Делается это просто:

<application
   android:name=".App"
	…

В теге `<application>` через атрибут `android:name`. И теперь всё будет минимально работать.

Ну хорошо, что-то у нас теперь хранится в классе `Application`, теперь вопрос: как нам это получить? Для этих целей у класса `Application` создается `Companion object`, который будет хранить экземпляр нашего `Application` в поле `**instance**`:

`companion object {`
   `lateinit var instance: App`
       `private set`
`}`

И в методе `onCreate()` мы эту переменную инициализируем:

`override fun onCreate() {`
   `super.onCreate()`
   `instance = this`
`}`

Теперь код выглядит примерно вот так:

`class App : Application() {`
   `val objectInAppClass = "Object"`
  
   `override fun onCreate() {`
       `super.onCreate()`
       `instance = this`
   `}`

  
   `companion object {`
       `lateinit var instance: App`
           `private set`
   `}`
`}`

И теперь из любого места нашего приложения мы можем получить `objectInAppClass` таким образом:

`val getObjectFromAppClass = App.instance.objectInAppClass`

Несмотря на удобство того, что объекты, которые находятся в классе `Application`, теоретически доступны на протяжении всей жизни приложения, нужно быть аккуратными. Всё же они могут быть уничтоженными системой и тогда, если кто-то захочет взять их из класса `App`, произойдет **NPE**.

## **Low-Memory**

В прошлых абзацах мы с вами коснулись темы **нехватки памяти**. Такое случается, когда у вас заканчивается оперативная память и система начинает убивать всё, что не используется прямо сейчас, чтобы отдать тому приложению, которое сейчас на первом плане. Поэтому система начинает закрывать все, что находится в фоновом режиме.

Когда памяти не хватает, у приложений вызывается коллбэк `onLowMemory()`, этот метод существует с _API 1.0_. Но, если приложение и так находится в фоне, то мы даже не узнаем про этот коллбэк, так как приложение будет уничтожено. Поэтому начиная с _API 14_ есть новый коллбэк — **`onTrimMemory(level: Int)`**.

В параметре `level` нам приходит уровень, насколько сильно система хочет освободить память.

> [!warning] В старом конспекте здесь ошибка
> Было написано, что уровень «принимает значения от 0 до 100». Это неверно. `level` — это **не процент**, а набор констант `ComponentCallbacks2.TRIM_MEMORY_*`:
>
> | Константа | Значение | Смысл |
> |---|---|---|
> | `TRIM_MEMORY_COMPLETE` | 80 | Процесс скоро убьют, освободи всё, что можно |
> | `TRIM_MEMORY_MODERATE` | 60 | Система сильно давит по памяти |
> | `TRIM_MEMORY_BACKGROUND` | 40 | Приложение в фоне, память нужна другим |
> | `TRIM_MEMORY_UI_HIDDEN` | 20 | UI не видно, освободи кэши UI |
> | `TRIM_MEMORY_RUNNING_CRITICAL` | 15 | Процесс на грани, не трогай ничего нужного |
> | `TRIM_MEMORY_RUNNING_LOW` | 10 | Мало памяти, пора чистить кэши |
> | `TRIM_MEMORY_RUNNING_MODERATE` | 5 | Память чуть просела |
>
> Числа не упорядочены по «силе» в одну шкалу — это просто **битовые флаги разных категорий**. Поэтому сравнивать `level > 50` бессмысленно: это смешает несравнимые вещи. Правильно — проверять конкретную константу:
>
> ```kotlin
> override fun onTrimMemory(level: Int) {
>     super.onTrimMemory(level)
>     if (level >= ComponentCallbacks2.TRIM_MEMORY_RUNNING_LOW) {
>         imageLoader.clearMemoryCache()
>     }
>     if (level >= ComponentCallbacks2.TRIM_MEMORY_UI_HIDDEN) {
>         database.clearCache()   // не сбрасываем сами данные
>     }
> }
> ```
>
> Здесь `>=` корректно, потому что внутри одной группы (`RUNNING_*`) константы упорядочены по возрастанию серьёзности: 5 < 10 < 15. Но сравнивать `RUNNING_LOW` (10) с `BACKGROUND` (40) через `>=` нельзя — они из разных групп.
>
> И главное: **это не гарантия.** `onTrimMemory` не даёт никаких обещаний, что приложение выживет. Он лишь позволяет увеличить шанс. Единственная настоящая защита от потери данных — сохранять состояние в `onSaveInstanceState` / `SavedStateHandle`.

Эти методы доступны как для класса `Application`, так и для остальных компонентов активити, фрагментов и т.д.

## **Работа с жизненным циклом**


Мы узнали, что есть такое понятие, как жизненный цикл в _Android_-приложениях. И мы в связи с этим можем эффективно управлять поведением нашего приложения. Мы можем делать это самостоятельно, то есть реализовывать какую-то свою логику обработки колбэков, а можем не изобретать велосипед и воспользоваться уже готовым решением от ребят из _Google_.

Прежде чем мы будем рассматривать конкретные вещи для взаимодействия с жизненным циклом, сделаю добавление к _Activity Lifecycle_. Дело в том, что есть специальный класс для работы с жизненным циклом — **`Lifecycle`,** и у него есть `enum class Event`, который содержит состояния, отражающие наши коллбэки жизненного цикла. Приведу их здесь, чтобы дальше было понятно, о чём идёт речь:

|   |   |
|---|---|
|`**Lifecycle.Event.ON_CREATE**`|`onCreate()`|
|`**Lifecycle.Event.ON_START**`|`onStart()`|
|`**Lifecycle.Event.ON_RESUME**`|`onResume()`|
|`**Lifecycle.Event.ON_PAUSE**`|`onPause()`|
|`**Lifecycle.Event.ON_STOP**`|`onStop()`|
|`**Lifecycle.Event.ON_DESTROY**`|`onDestroy()`|
|`**Lifecycle.Event.ON_ANY**`|Применяется при любом коллбэке|

## **ProcessLifecycleOwner**

Этот класс используется для отслеживания процесса всего приложения, можно его расценивать как собрание воедино всех ваших активити. Нужно учитывать, что:

|   |   |
|---|---|
|1|`**Lifecycle.Event.ON_CREATE**` будет получен только один раз.|
|2|`**Lifecycle.Event.ON_DESTROY**` не будет получен никогда.|
|3|Все события жизненного цикла будут подчиняться следующим правилам:<br><br>- `**ProcessLifecycleOwner**` вернёт `**Lifecycle.Event.ON_START**`;<br>- `**Lifecycle.Event.ON_RESUME**` единожды при создании активти;<br>- `**Lifecycle.Event.ON_PAUSE**`, `**Lifecycle.Event.ON_STOP**` будут вызваны с задержкой после того, как последнее активити пройдет через эти стадии.|

Этот класс может пригодиться, когда вам нужно отслеживать перемещение состояния приложения из бэкграунда на передний план и обратно. И вам не нужна супер точность по времени при получении состояний жизненного цикла.

## **Lifecycle**

Мы уже начали о нем говорить в самом начале, давайте продолжим.

Это класс, который содержит информацию о состоянии жизненного цикла компонента, и позволяет другим объектам за этим следить.

Помимо `**Events**`, которые мы рассмотрели в начале, этот класс ещё хранит `**States**` (состояния). `**Events**` — это само событие, то есть наш компонент перешел из одного состояние в другое, а `**States**` — это и есть сами состояния.

> [!warning] Подход с аннотациями устарел
> Ниже показан способ через `@OnLifecycleEvent` и пустой интерфейс-маркер `LifecycleObserver`. Это API из 2017 года, он плохо подсказывает IDE и не даёт типизации. С тех пор AndroidX добавил `DefaultLifecycleObserver` — **это то, что надо использовать сейчас**. Актуальный вариант ниже, старый оставлен для понимания легаси-кода.

## Актуально: `DefaultLifecycleObserver`

Идея та же — подписаться на жизненный цикл, — но теперь ты **реализуешь интерфейс с методами**, а не вешаешь аннотации. IDE подсказывает имена, компилятор проверяет сигнатуры.

```kotlin
class LifecycleListener : DefaultLifecycleObserver {

    override fun onStart(owner: LifecycleOwner) {
        // ... логика на старте
    }

    override fun onStop(owner: LifecycleOwner) {
        // ... логика на остановке
    }
}
```

Подписка — ровно та же:

```kotlin
lifecycle.addObserver(listener)
```

Что изменилось по сравнению с аннотациями:

- **Нет `Lifecycle.Event.ON_START`** — метод называется `onStart(owner: LifecycleOwner)`. Само событие не нужно: вызвали метод — значит событие произошло.
- **Нет `ON_ANY` в виде аннотации.** Чтобы поймать всё, реализуй `LifecycleEventObserver`:

```kotlin
class AnyEventListener : LifecycleEventObserver {
    override fun onStateChanged(source: LifecycleOwner, event: Lifecycle.Event) {
        when (event) {
            Lifecycle.Event.ON_START -> { /* ... */ }
            Lifecycle.Event.ON_STOP -> { /* ... */ }
            else -> { /* ... */ }
        }
    }
}
```

- **`Lifecycle.Event.ON_ANY` — внутренняя константа** (с `@RestrictTo`). В пользовательском коде её использовать не нужно: `when` по `event` в `onStateChanged` покрывает все состояния.

### Когда что использовать

| Задача | Инструмент |
|--------|-----------|
| Реагировать на 1-2 конкретных события | `DefaultLifecycleObserver` |
| Нужно видеть **все** события и фильтровать вручную | `LifecycleEventObserver` |
| Нужна реактивность (`collect` во время `STARTED`) | `repeatOnLifecycle(Lifecycle.State.STARTED)` — об этом в заметке про корутины |

## Старый подход (legacy)

Для того чтобы реализовать обозрение жизненного цикла компонента, нам нужно сначала создать класс, который будет слушателем, он должен реализовывать интерфейс `LifecycleObserver`:

`class LifeCycleListener : LifecycleObserver {`
   `@OnLifecycleEvent(Lifecycle.Event.ON_START)`
   `fun start() {`
       `// ...`
   `}`

   `@OnLifecycleEvent(Lifecycle.Event.ON_STOP)`
   `fun stop() {`
       `// ...`
   `}`
`}`

Если заглянуть внутрь `LifecycleObserver`, то мы не увидим там методов для реализации, это интерфейс-маркер. По сути, мы можем создавать какие угодно методы и через аннотации помечать, какой метод и когда будет выполнен. В примере выше экземпляр класса `LifeCycleListener` будет исполнять методы когда компонент, на который он подписан, будет проходить через эти стадии жизненного цикла.

Теперь осталось только, как говорится, «оформить подписочку» для этого в тех активити, которые мы хотим обозревать:

lifecycle.addObserver(lifeCycleListener)

Вот и вся премудрость, теперь обо всех жизненных изменениях наш `LifeCycleListener` будет в курсе. Это возможно потому, что активити является _LifecycleOwner_. Именно этот интерфейс и добавляет метод `getLifecycle` (поле `**Lifecycle**` в случае _Kotlin_), и мы можем получать информацию о жизненном цикле.
