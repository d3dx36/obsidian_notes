## 1. Пирамида тестирования в Android

В контексте Android UI-тесты делятся на два основных типа:

1. **Инструментальные тесты (Instrumented Tests):** Выполняются на реальном устройстве или эмуляторе (`androidTest/`). Имеют доступ к Android-контексту (`Context`).
    
2. **Локальные тесты скриншотов/UI (Screenshot/Robolectric Tests):** Выполняются на JVM хост-машины (`test/`). Работают значительно быстрее инструментальных.
    

## 2. Основной стек инструментов

### Котлиноцентричные фреймворки (Рекомендуемые)

|**Инструмент**|**Для чего используется**|**Особенности**|
|---|---|---|
|**[[Espresso]]**|Классический UI (Imperative View System)|Синхронизирует шаги теста с UI-потоком приложения. Меньше "флапающих" тестов.|
|**[[Compose-Test-Framework]]**|Jetpack Compose (Declarative UI)|Использует семантическое дерево (`SemanticTree`) для поиска элементов вместо привычных `R.id`.|
|**[[Kaspresso]]**|DSL-обертка над Espresso и UI Automator|Решает проблему Flaky-тестов, встроенное логирование, понятный синтаксис (через `Kakao`).|

### Системный уровень и Кроссплатформенность

- **[[UI Automator]]:** Используется для тестирования системных UI-компонентов (шторка уведомлений, системные диалоги разрешений, переключение в настройки, взаимодействие с другими приложениями).
    
- **[[Appium]]:** Черный ящик (Black-box). Используется в кроссплатформенных командах (один тест на iOS и Android). Медленнее нативных инструментов.
    

## 3. Паттерны проектирования в UI-тестах

### Паттерн Page Object (Robot Pattern)

В Android-разработке классический Page Object чаще реализуют в виде **Robot Pattern** (популяризировал Jake Wharton). Он разделяет _«что тестируется»_ (логику теста) и _«как это реализовано на UI»_ (поиск элементов).

#### Пример реализации (Robot Pattern на Котлине):

Kotlin

```
// Описание экрана и действий (Робот)
class LoginRobot {
    fun enterEmail(email: String) {
        onView(withId(R.id.et_email)).perform(typeText(email), closeSoftKeyboard())
    }
    fun enterPassword(password: String) {
        onView(withId(R.id.et_password)).perform(typeText(password), closeSoftKeyboard())
    }
    fun clickSubmit() {
        onView(withId(R.id.btn_login)).perform(click())
    }
    fun checkErrorIsDisplayed() {
        onView(withText(R.string.error_invalid_credentials)).check(matches(isDisplayed()))
    }
}

// Сам тест (Выглядит как человекочитаемый сценарий)
@Test
fun loginWithInvalidCredentials_ShowsError() {
    LoginRobot().apply {
        enterEmail("wrong@email.com")
        enterPassword("12345")
        clickSubmit()
        checkErrorIsDisplayed()
    }
}
```

## 4. Борьба со стабильностью (Flaky Tests)

> [!danger] Главная проблема UI-тестов — Flakiness
> 
> **Flaky test** — тест, который при неизменном коде может то падать, то проходить (из-за задержек анимаций, сети, медленного рендеринга эмулятора).

### Способы решения:

1. **Отключение анимаций на тестовом устройстве:**
    
    Перед прогоном тестов через ADB отключаются анимации окон, переходов и длительность аниматора:
    
    Bash
    
    ```
    adb shell settings put global window_animation_scale 0
    adb shell settings put global transition_animation_scale 0
    adb shell settings put global animator_duration_scale 0
    ```
    

````
2. **Использование Idling Resources:**
   Механизм Espresso, позволяющий тесту «ждать», пока приложение выполняет фоновый сетевой запрос или асинхронную операцию. Тест возобновляется только тогда, когда приложение переходит в состояние `Idle` (покой).
3. **Использование Kaspresso фреймворка:**
   В Kaspresso встроена автоматическая защита от Flaky-тестов (механизм ретраев — `flakySafely`), которая пытается повторить упавший шаг в течение нескольких секунд, если элемент не успел отрисоваться.

## 5. Тестирование Jetpack Compose UI

В Compose нет классических `View ID`. Элементы ищутся по семантическим свойствам (текст, описание, теги).

```kotlin
class ComposeLoginTest {

    @get:Rule
    val composeTestRule = createAndroidComposeRule<MainActivity>()

    @Test
    fun testLoginButtonClicks() {
        // Поиск по семантическому тегу (Modifier.testTag("login_button"))
        composeTestRule.onNodeWithTag("login_button").performClick()
        
        // Проверка по тексту
        composeTestRule.onNodeWithText("Welcome Back").assertIsDisplayed()
    }
}
````

## 6. Screenshot Testing (Тестирование Скриншотов)

Современный тренд в Android-разработке. Вместо проверки логики кликов, инструмент делает снимок экрана/компонента и попиксельно сравнивает его с эталонным изображением (Baseline).

- **Популярные библиотеки:** [[Paparazzi]] (от Cash App), [[Showkase]] (от Airbnb), Roborazzi.
    
- **Плюс:** Огромная скорость, так как Paparazzi работает на JVM без запуска эмулятора. Отлично подходит для изоляции дизайн-систем.
    

> [!tip] Резюме для CI/CD
> 
> UI-тесты дорогие в поддержке и медленные. Оптимальный пайплайн: **Unit-тесты** на каждый PR $\rightarrow$ **Screenshot-тесты** для проверки верстки $\rightarrow$ **E2E UI-тесты** (Kaspresso/Espresso) только на критические бизнес-сценарии (авторизация, покупка) перед релизом.
